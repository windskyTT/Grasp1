# 问题9：PPO 配置与训练稳定性

**严重程度：P1**

最新代码已经正确计算：

```python
gamma = 0.996 ** (control_dt / 0.2)

lam = 0.95 ** (control_dt / 0.2)
```

这部分不需要再次修改。

但是，本地2次更新有一个需要关注的数据：

| 指标 | 第1次更新 | 第2次更新 |
|---|---:|---:|
| Value Loss | 3.193 | 1.272 |
| 更新后 KL | **0.1317** | **0.0829** |
| Desired KL | 0.01 | 0.01 |

当前报告中的更新后 KL 明显高于 `desired_kl=0.01`。

不过，**`train.py` 自定义计算的是 PPO 更新结束后的 KL，不一定等于 RSL-RL 在各 mini-batch 更新期间用于自适应学习率调节的 KL**。

不能直接据此断定 PPO 算法实现错误。

### 解决方案

首先保持：

```python
learning_rate = 3e-4
num_steps_per_env = 32
num_learning_epochs = 5
num_mini_batches = 4
gamma = 0.999666054
lam = 0.995734681
```

然后在现有 `train.py` 中检查：

- 实际学习率变化；
- 每次 PPO 更新的 KL；
- Value Loss；
- Surrogate Loss；
- Entropy；
- 动作标准差；
- 关节目标饱和；
- 完成回合数和成功率。

建议逐阶段验收：

| 阶段 | PPO 更新 | 验收重点 |
|---|---:|---|
| Smoke | 2 | 训练入口和数值有限性 |
| 基础 | 10 | 小规模连续更新 |
| 短期 | 100 | 物理异常、奖励变化 |
| 中期 | 500 | 接触学习是否改善 |
| 深入 | 1000 | PPO 是否稳定、是否出现自主抬升 |
| 后续 | 2000+ | 仅在前面稳定时继续 |

训练更新数只是检查节点，不是成功保证。

若出现明显的 Value Loss 发散或物理异常，先查原因，不同时调整多个 PPO 参数。

# GUI 成功抓取的显示问题

**严重程度：P2**

涉及：

`scripts/rsl_rl/play.py`

当前 `play.py` 的推理流程正确：

```python
with torch.inference_mode():
    actions = policy(obs)
    obs, _, dones, extras = env.step(actions)
```

没有使用脚本控制器代替 PPO。

但因为成功判据已经恢复为：

```python
success = lift > 0.10
```

环境会在成功后立即触发 Episode 结束和自动 Reset。

因此，即使 PPO 学会了抓取，也可能出现：

```text

   ↓
立即触发 success
   ↓
自动 Reset
   ↓
GUI 中成功姿态很快消失
```

### 解决方案

**不修改训练环境的成功判据或奖励。**

建议仅在现有 `play.py` 的展示与评估功能中完善：

| 功能 | 修改要求 |
|---|---|
| 指定物体 | 允许从现有训练集指定物体名称 |
| 指定随机种子 | 保留 |
| 指定 checkpoint | 保留严格契约检查 |
| 成功统计 | 输出真实成功回合数与总回合数 |
| GUI 渲染 | 保留真实策略控制过程 |
| 成功瞬间 | 使用实际渲染帧或预 Reset 捕获机制记录 |
| 环境物理 | 不修改 |
| 策略动作 | 只能来自 `policy(obs)` |

这里要注意：`env.step()` 返回时，成功环境通常已经 Reset。因此，**不能简单在 `env.step()` 返回后截图，声称截到了成功姿态**。

如果需要可靠保存成功瞬间，应使用 Isaac Lab 已有的预 Reset 录制或渲染机制，并验证捕获时机。

不应该通过以下方法制造成功画面：

- 暂停训练并人为上抬物体；
- 使用脚本式抓取动作；
- 修改物体位置；
- 更换不兼容的 checkpoint；
- 将失败截图标记为成功。

真正的 GUI 验收必须来自当前 PPO checkpoint 的实际策略执行。
